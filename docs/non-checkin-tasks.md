# 非签到任务扩展边界

状态：当前核心继续专注每日签到；等出现第一个明确的非签到需求后，再以该需求验证并实现通用任务
层，不直接把现有 Checker 改成含义模糊的通用接口。

日期：2026-09-07

## 1. 为什么需要单独决策

当前 Runner 的语义非常具体：按站点枚举账号、每天执行一次签到、成功后写入当天终态，并发送
签到结果通知。这些规则适合签到，但不能自然表达持续监控、文件下载、备份和多阶段流程。

过早把 `Checker` 改名为 `Task` 只会隐藏差异。真正支持其他脚本需要先明确运行对象、成功状态、
重复策略、产物和通知条件。

## 2. 任务类型与现有框架适配度

| 任务类型 | 示例 | 能否直接作为 Checker | 缺少的能力 |
| --- | --- | --- | --- |
| 每日幂等账号操作 | 签到、领取每日奖励 | 可以 | 按新增站点指南接入 |
| 周期状态监控 | 页面变化、服务状态、库存监控 | 不适合 | 观测值、变化比较、静默策略、恢复事件 |
| 下载或导出 | 下载报表、抓取文件、生成归档 | 不适合 | 产物路径、校验、断点续传、保留策略 |
| 备份与同步 | 数据库备份、文件同步 | 不适合 | 源与目标、增量游标、一致性和恢复验证 |
| 多阶段流程 | 登录、提交、等待、再次确认 | 不适合 | 状态机、阶段超时、补偿和恢复点 |
| 一次性维护命令 | 清理状态、迁移配置 | 不适合定时 Runner | 独立命令、确认范围和审计输出 |

判断标准不是脚本是否访问网站，而是它能否遵守“每个账号每天得到一个终态”的模型。满足这一点
的领取类脚本仍可以作为 Checker；其余任务应使用新的任务层。

## 3. 可以复用的现有组件

非签到任务可以继续复用以下基础能力：

- `SafeHttpClient` 的 HTTPS、同主机重定向和有限网络重试。
- `security.py` 的凭据遮罩和 CI 掩码。
- 环境变量解析、基础地址校验和青龙配置增量升级方式。
- 通知渠道的签名与 HTTP 发送代码。
- `site_catalog.py` 的集中元数据思路，但非站点任务应使用独立目录和命名空间。

现有通知消息格式包含签到标题和签到状态，不能直接复用到监控或备份报告。未来可以抽取通知传输
层，但每类任务应保留自己的消息内容和发送条件。

## 4. 不能直接复用的语义

以下部分与每日签到绑定，不应在没有具体需求时泛化：

- `Checker.accounts` 假设执行对象是账号。
- `SUCCESS`、`ALREADY_DONE`、`FAILED` 表示当天签到结果。
- `DailyState` 只表达某账号在某日期已经到达终态。
- Runner 只在本次产生账号结果时通知，并将失败留给下一次定时执行。
- `run --site`、Actions 站点下拉项和青龙站点任务都以签到站点为单位。
- 汇总消息固定使用 CheckinTools check-in 文案。

例如，监控任务的“状态没有变化”通常是一次成功观测，但不应每天只执行一次，也不应每次发送
通知；备份任务的“文件已存在”可能需要校验产物，而不是等同于 `ALREADY_DONE`。

## 5. 未来通用任务层的最小模型

出现明确需求后，建议在 Checker 之上新增任务层，而不是替换现有接口。最低需要以下概念：

```text
TaskDefinition
├─ task_id / display_name
├─ task_kind
├─ configuration keys
└─ schedule and concurrency policy

Task
├─ enumerate_items()
├─ execute(item, context) -> TaskResult
└─ state_identity(item)

TaskResult
├─ outcome
├─ summary
├─ retry policy
├─ observations
└─ artifacts

StateStore
├─ namespace and schema version
├─ load/save
└─ retention and migration
```

其中 `outcome` 应由任务类型定义，不能继续强制所有任务使用签到状态。执行上下文至少包含当前时间、
运行 ID、状态存储和临时目录；产物必须有明确路径、校验结果和保留责任。

通知应由事件策略决定，例如：

- 签到：有实际账号结果时发送。
- 监控：只在状态变化、恢复、失败或需要人工处理时发送。
- 备份：完成、校验失败或连续失败达到阈值时发送。
- 下载：新产物可用、产物损坏或需要重新认证时发送。

## 6. 与现有签到功能的兼容方式

未来引入任务层时，应保留以下兼容性：

1. `Checker` 和当前 `run --site` 命令继续可用。
2. 使用适配器把 Checker 暴露为 `daily-checkin` 类型任务，不一次性重写三个站点。
3. 现有每日状态文件继续由签到适配器读取，避免重复执行。
4. 新任务使用独立状态命名空间和版本，不与签到状态文件混写。
5. GitHub Actions 和青龙入口按任务类型显式创建，避免一个通用任务承担互相冲突的调度策略。

## 7. 首个非签到任务的落地顺序

收到具体需求后按以下顺序实现：

1. 写清触发频率、输入、成功证据、重试、通知和产物生命周期。
2. 判断它是否仍符合每日幂等账号操作；符合则继续使用 Checker。
3. 不符合时，只为该任务抽取所需的最小通用接口和状态能力。
4. 为现有 Checker 添加适配器，验证 CLI、通知和状态行为不变。
5. 接入一种运行平台并验证真实运行，再扩展到其他平台。
6. 第二种非签到任务出现后，复查公共抽象是否确实可复用。

这种顺序让通用接口由真实差异推动，并给现有签到功能保留稳定的兼容边界。

## 8. 当前结论

项目目前可以方便地增加每日领取类脚本。监控、下载、备份和多阶段流程可以复用 HTTP、安全、配置
及部分通知传输代码，但需要新的结果、状态和调度模型。

在没有具体非签到需求时，不新增空泛的 `Task` 接口或通用 Runner。未来第一个非签到脚本应同时
提供需求说明和最小任务层实现，并把本文件更新为已经验证的设计。
