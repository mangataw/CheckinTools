# 站点注册与插件机制决策

状态：采用受信任的集中清单和静态平台文件生成；暂不引入运行时插件发现。

## 当前决策

内置站点统一声明在 `src/checkin_tools/sites.toml`。Checker 按站点 ID 约定加载：

```text
站点 ID：example
模块：checkin_tools.checkers.example
入口：SiteChecker
```

`tools/sync_sites.py` 根据同一份清单生成 GitHub Actions 和青龙所需的静态配置。生成结果提交到
仓库，并由 CI 检查是否与清单一致。站点业务、测试 fixture 和使用说明仍由开发者实现。

完整接入步骤参阅 [新增签到站点指南](adding-a-site.md)。

## 为什么不使用运行时插件发现

GitHub Actions 在解析工作流时不能运行项目 Python；青龙订阅也必须预先看到包含 cron 元数据的
任务文件。因此，无论 Checker 如何加载，两个平台都需要可审查、已提交的静态配置。

当前站点全部随主仓库发布，数量有限，也没有独立安装、独立版本或第三方依赖隔离需求。此时使用
目录扫描、用户指定模块路径或 Python entry points 会增加任意导入、版本兼容和来源信任问题，
却不能消除平台静态文件。

因此，`sites.toml` 同时作为站点元数据来源和受信任模块白名单；程序不扫描整个目录，也不接受
用户通过配置指定任意模块。

## 当前边界

- 只加载主仓库中经过审查并写入清单的站点。
- 新增站点需要修改主仓库并随版本发布。
- GitHub Actions 与青龙的静态文件必须在修改清单后重新同步并提交。
- 真实凭据不进入清单或生成器，由部署平台单独配置。

## 重新评估条件

出现以下实际需求时，再设计插件机制：

- 站点扩展需要在独立仓库发布，无需修改主仓库。
- 不同部署需要独立安装或升级部分站点及其依赖。
- 多个维护者的发布周期使集中发布成为实际瓶颈。
- 形成不依赖 GitHub Actions 和青龙静态接入的本地扩展生态。

届时需要先定义带版本的 Checker API、站点 ID 冲突规则、敏感值注册、依赖隔离、来源信任、
加载失败隔离，以及两个部署平台的静态文件生成方式。站点数量增加本身不足以引入插件系统。
