# 站点注册与插件机制决策

状态：当前采用集中元数据加显式注册；暂不引入运行时插件加载。

日期：2026-09-07

## 1. 背景

CheckinTools 当前包含三个内置签到站点，并同时支持本地 CLI、GitHub Actions 和青龙 Docker。
站点 ID、显示名称、配置键和默认地址已经集中在 `site_catalog.py`，但 Checker 类、GitHub Actions
Secrets 和青龙任务入口仍需要显式接入。

这里需要决定是否继续显式维护，或改为自动扫描 Python 文件、加载 Python entry points 等插件
机制。目标是降低新增站点的遗漏风险，同时保持部署简单、行为可审查和凭据边界清晰。

## 2. 方案比较

| 方案 | 优点 | 主要成本与限制 | 当前判断 |
| --- | --- | --- | --- |
| 集中元数据加显式注册 | 代码路径清楚；站点顺序稳定；测试容易检查遗漏；无需额外安装协议 | 新站点仍需登记 Checker 和平台静态入口 | 采用 |
| 扫描 `checkers/` 目录并导入 | 少写一处注册代码 | 文件名不能表达配置、顺序和平台信息；导入任意文件扩大启动副作用；错误更晚暴露 | 不采用 |
| Python entry points | 可让第三方站点独立打包和安装；适合跨仓库扩展 | 需要公共 API 版本、依赖冲突处理、插件可信策略和发现错误模型 | 暂缓 |
| 配置驱动的模块路径 | 无需修改核心注册表 | 用户配置可触发任意模块导入；拼写、依赖和安全问题转移到运行时 | 不采用 |

## 3. 决策

现阶段继续使用以下组合：

1. `site_catalog.py` 维护所有内置站点元数据。
2. `checkers/__init__.py` 显式登记 Checker 类型，并在构建时检查它与站点目录完全一致。
3. CLI 和青龙运行桥接从站点目录读取合法站点、配置键和账号判断依据。
4. GitHub Actions 下拉选项、Secrets 映射、青龙任务文件和订阅正则继续显式维护。
5. 测试从站点目录生成预期列表，用失败提示暴露静态平台配置遗漏。

这套方式把 Python 运行时的重复定义降到较低水平，同时保留平台文件的可读性。GitHub Actions
无法在工作流解析阶段执行项目 Python 代码，青龙也需要在订阅扫描时看到带 cron 元数据的静态
任务文件，因此运行时插件发现不能消除这些平台接入步骤。

## 4. 暂不使用目录扫描的原因

目录扫描看似可以省去一行注册代码，但不能自动解决账号配置、Secrets、青龙入口、用户文档和
测试 fixture。它还会让导入行为取决于文件系统内容和命名顺序，使一个损坏或带副作用的模块影响
整个程序启动。

本项目处理 Cookie 和通知密钥，站点实现应经过代码审查并明确进入构建列表。可见的显式注册比
隐式扫描更符合当前安全边界。

## 5. 重新评估 Python 插件的触发条件

出现以下任一需求时，再评估 Python entry points：

- 用户需要安装独立仓库维护的站点扩展，而不修改 CheckinTools 主仓库。
- 不同部署只需要部分站点，并希望各站点独立发布和升级依赖。
- 内置站点由多个维护者频繁并行开发，集中发布流程成为实际瓶颈。
- 出现只面向本地运行的扩展生态，不要求自动生成 GitHub Actions 或青龙任务。

站点数量增加本身不是唯一理由。如果新增站点仍由同一仓库维护，并且都需要同步 Actions 和青龙，
显式注册仍然更简单。

## 6. 未来插件协议的最低要求

如果触发重新评估，插件方案至少应先定义：

- 固定的 entry point 分组，例如 `checkin_tools.checkers`。
- 可版本化的 Checker API 和兼容范围。
- 站点 ID 冲突、重复注册和加载失败的处理规则。
- 插件自己的配置声明、敏感字段和脱敏注册方式。
- 第三方依赖冲突及最低 Python 版本策略。
- 插件来源和安装信任边界；发现插件不等于隔离插件代码。
- 未安装插件时状态文件、CLI 参数和通知内容的兼容行为。
- GitHub Actions 与青龙所需的独立部署说明。

插件加载失败应只影响对应扩展，错误信息必须脱敏；核心站点和其他插件应继续可用。达到这些条件
前，不引入半自动的模块导入机制。

## 7. 迁移路径

未来采用 entry points 时，可以保留 `SiteDefinition` 作为元数据结构，并按以下顺序迁移：

1. 为站点定义和 Checker 接口增加明确的 API 版本。
2. 让内置站点先通过与第三方相同的加载适配层注册，验证行为不变。
3. 增加插件发现、冲突和故障隔离测试。
4. 再允许安装外部站点包，并明确其配置和平台部署步骤。
5. 最后评估是否仍需要保留内置站点的显式构建表。

在此之前，新增站点继续遵循 [新增签到站点指南](adding-a-site.md)。
